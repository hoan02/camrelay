camrelay / Technical guide

From remote P2P camera to a local RTSP stream

camrelay is a self-hosted bridge for cameras that are reachable through a compatible P2P service. It keeps the camera connection local to your infrastructure while exposing a familiar TCP endpoint for players, NVRs, and automation.

Architecture and data flow

What happens when a camera tunnel starts.

01

Provider profile

camrelay loads the provider server and application credentials from the brand profile. These values identify the client application to the signaling service.

02

P2P handshake

The Rust handshake locates the device by serial number, prepares a channel, and negotiates a direct or relayed UDP path when the service and device allow it.

03

PTCP session

A PTCP session encapsulates TCP bytes inside UDP packets. Each local client is assigned a multiplexed realm over the camera tunnel.

04

Local RTSP

FFmpeg, Frigate, VLC, or another consumer connects to the configured local port and speaks the camera's normal RTSP path through the relay.

Protocol layers

SignalingDahua HTTP-like DHGET/DHPOST requests locate the device and create a channel.
TransportUDP carries the P2P/PTCP traffic. NAT traversal may produce a direct path or require relay infrastructure.
MultiplexingOne camera session can carry multiple TCP clients by assigning each connection its own PTCP realm.
ApplicationRTSP is not rewritten by camrelay; the local TCP stream is passed through to the remote device.

Runtime model

Rust async serviceTokio runs the web server, tunnel tasks, heartbeat loop, and per-client reader/writer tasks concurrently.
JSON storageConfiguration is read from the working directory. Passwords and API tokens are stored as plaintext and must be protected.
Web/API controlThe dashboard and REST API operate on the same camera, provider, tunnel, and token models.

Compatibility and IMOU

A provider label is configuration, not a compatibility guarantee.

Verified path

A model and firmware combination that has been tested end-to-end: signaling, tunnel, RTSP authentication, and sustained playback.

IMOU experimental

IMOU is shown as an experimental provider profile. The profile does not include credentials and does not claim that every IMOU camera uses the same backend or protocol.

Custom provider

A user-managed brand profile with its own server and app credentials. It must be tested against authorized hardware before unattended use.

Security boundaries

  • The web server has no built-in TLS; keep it on a trusted network or put it behind a TLS reverse proxy.
  • Provider credentials, device passwords, and API tokens are sensitive runtime state.
  • Use only devices and cloud accounts you are authorized to administer.
  • Treat a working relay as network access to a camera, not as an authorization mechanism.

Operations and troubleshooting

  • Start with one camera and verify the local RTSP URL with ffplay before adding an NVR.
  • If the tunnel is running but RTSP fails, check device credentials, channel path, and remote RTSP port.
  • If the handshake fails, check serial number, provider profile, app credentials, cloud reachability, and device online status.
  • Use the tunnel status and service logs to separate signaling failures from RTSP/application failures.

Integration notes

For Frigate or FFmpeg, use the local RTSP URL shown on the camera card. Keep camrelay and the consumer on the same host or reachable LAN segment, reserve one local port per camera, and monitor the relay process as part of the NVR stack.

rtsp://<camera-user>:<camera-password>@127.0.0.1:<local-port>/cam/realmonitor?channel=1&subtype=0
